# 有迹：面向创作者的多智能体创作平台 · 技术方案

AI+软件创新 | 团队编号 47191919 | 软件版本 0.8.0 | 产品基线 2026-10-13

**作品名称**：有迹：面向创作者的多智能体创作平台。**产品定位**：面向个人内容创作者的多智能体创作与运营助手。

有迹把「账号定位 → 资料检索 → 四角色协作创作 → 主编审核 → 人工作业确认 → 运营复盘」串成一条可回溯的网页工作流。系统自建分类证据检索、主张级引用校验、有界执行与费用守卫、可追溯写作改进协议（内容风洞）四层机制，并把每一次模型调用、每一份资料版本、每一版稿件的审核结论冻结保存。用户始终保留修改权与最终确认权。

本方案的判断依据为交付基线 2026-10-13（源码提交 79f53e8）的源码、工程测试与真实模型运行记录；所有数据均可按附录索引复核。

## 一、产品概述与定位

### （一）背景：个人创作者缺的不是「会写的模型」，而是可核对的写作流程

大模型已经把「生成一段文字」的门槛降到很低，但个人创作者每天面对的真实任务并不是生成一段文字，而是完成一次可交付的内容生产：判断这批读者关心什么、从自己的资料里挑出可用依据、决定这一篇讲哪个角度、把表达改到符合账号语气、确认稿子里每一句结论都站得住、导出成可继续编辑的文档，再在一周后用真实数据判断上一篇哪里没讲清。

把这些动作分散在聊天窗口、文档和表格里，会产生三个具体损失：

1. **依据丢失**。参考资料和最终稿件脱节，事后没人能说清「这句话是从哪份资料来的」。写作参考（别人的表达结构）与可核查事实（产品规格、价格、适用条件）混在一起，是被引错、写错的高频来源。
2. **版本混乱**。改稿即覆盖，旧结论配新正文；审核意见指向的句子在下一版已经不存在。
3. **执行不可控**。一次生成跑到一半失败，重试可能重复计费；浏览器一关，任务状态就断。

有迹的设计起点就是这三条损失，而不是「再套一层提示词」。

### （二）产品定位与目标用户

**产品类型**：算法驱动的桌面/本机 Web 应用（含 Windows 免安装运行包与源码部署两种形态），面向中文内容创作场景。

**目标用户**：个人博主与 1—3 人小型内容团队，尤其是需要在「有资料、有事实约束」的前提下持续产出的垂类创作者——数码家电选购、家居装修、美妆护肤、学习资料整理等。

**核心场景**：小红书文字图文稿；抖音口播稿与分镜脚本。

**与同类方案的差异化**（不是功能清单的差异，而是约束机制的差异）：

| 维度 | 通用对话工具 | 通用内容编辑器 | 有迹 |
| --- | --- | --- | --- |
| 资料与稿件的关系 | 手工粘贴，随对话丢失 | 无来源追踪 | 检索快照冻结，引用逐字可定位 |
| 写作参考与事实依据 | 混在同一上下文 | 不区分 | 三组解耦：方法 / 样例 / 事实，样例永不进事实位 |
| 审核结论 | 模型自评即可信 | 无审核 | 审核不掌握批准权，服务端另设必过项与版本守卫 |
| 失败与费用 | 重试即重算 | 不涉及 | 调用前持久预留、用量未知即阻断、节点幂等可恢复 |
| 改稿依据 | 「模型觉得可以更好」 | 人工凭经验 | 作者确认问题 → 读稿证据 → 材料证据 → 局部补丁 → 原条件复查 |

### （三）交付形态

- **Windows 免安装运行包**：内置 Python 运行时，双击启动器即在本机拉起服务并打开浏览器，无需安装 Python、PostgreSQL 或 Node，无需管理员权限；模型与联网能力使用用户自己的账号与密钥。
- **源码部署**：Python 3.12 + FastAPI + PostgreSQL + LangGraph，API 与 Worker 双进程，适合二次开发与内网部署。

两种形态共用同一套业务代码与测试基线。

### （三）创新应用一：三组解耦的分类证据检索

普通 RAG 把所有资料放进同一个向量池，于是「写法参考」会被当成「事实依据」引用——参考别人的表达结构是正当的，把他人的产品结论搬进自己的稿件是错误陈述。有迹按**证据角色**把资料解耦成三组，各自拥有独立的过滤条件、检索语义、配额与降级路径：

| 组 | 角色 | 允许进入 | 检索查询构造 | 配额 |
| --- | --- | --- | --- | --- |
| `methods` | 通用写作方法 | 当前领域或通用领域；渠道与形式适用 | 形式标签 + 写作结构词 | 2 条 |
| `examples` | 写法参考 | 与任务领域有交集，渠道与形式完全匹配 | 领域标签 + 形式标签 + 结构词 | 3 条 |
| `facts` | 可核查材料 | 限当前账号、有效版本、用户所选资料、主题相关 | 用户原始主题 | 4 条 |

关键设计在于**过滤先于计算**：`owner/account 隔离 → 资料有效状态 → 图谱可见性 → 证据角色 → 领域交集 → 渠道/形式 → 所选资料 → 事实主题门控 → 向量召回`。权限、状态、领域、形式全部在向量计算之前完成，因此越权资料不会被算进相似度，计算也不浪费在无权候选上。

两项针对内容场景的硬约束：

- **产品型号精确匹配**：查询中出现型号类标识（字母与数字组合）时，`facts` 候选必须包含全部型号串，否则淘汰。阻止「A 型号参数」被移植到「B 型号」。
- **事实主题门控**：`facts` 候选须通过词项校验——词项交集为空、或长查询命中不足 2 个词、或覆盖率低于 10%，直接淘汰。避免长问题里偶然的双字词匹配被当成相关。

排序采用确定性线性组合：`rank_score = 0.8 × cosine_similarity + 0.2 × term_coverage`。这是二次重排而非交叉编码器，权重为工程取值，可被后续消融实验替换。

### （四）创新应用二：主张级引用闭环

| 层级 | 校验内容 | 失败后果 |
| --- | --- | --- |
| ① 来源存在 | `source_id` 必须存在于本次冻结快照 | 拒绝该输出 |
| ② 引用定位 | `quote` 必须是来源正文的逐字子串 | 拒绝该输出 |
| ③ 审核定位 | 审核 `claim_map` 中的 `excerpt` 必须出现在当前稿件正文 | 拒绝该输出 |
| ④ 批准权限 | 必过项齐全、审核绑定当前稿件版本与内容哈希、无未解决高严重度问题 | 不得确认 |

三层校验全部由服务端程序执行，模型无法绕过。模型返回 `approved` 不等于稿件通过——第四层守卫把「模型说可以」与「系统允许确认」分开，人工修改后旧审核立即失效，必须复审；过期 Worker 不能提交覆盖新版本的结果。

当研究角色判定核心事实缺口存在时，系统收窄而不是补造：允许继续生成，但提示词约束按已有信息收窄选题与标题承诺；不得补造规格、价格、功效或个人经历；审核即使自述通过也会被记录为需要人工处理；最终由用户明确「人工采用」后才能导出，并在文档中标注未通过 AI 审核。

### （五）创新应用三：内容风洞——可追溯的写作改进协议

常规「AI 改稿」有三个答不上的问题：读者哪里没看懂、资料到底支持不支持、改完到底有没有变好。内容风洞把它拆成四个可审计阶段，核心是**用 ID 代替文本**的间接层：

| ID | 作用 |
| --- | --- |
| `span_id` | 把稿件切成可定位段落槽位；模型只能选择槽位，不能计算字符偏移 |
| `excerpt_id` | 把当前稿件切成读稿证据片；答案只能引用 ID，由程序提取原文 |
| `evidence_id` | 把材料切成证据片；核验时必须引用 ID |

阶段约束是单向收紧的：读稿只允许 `pass`/`unclear` 且 `pass` 必须给出有效 `excerpt_id`；核验阶段只要读稿是 `unclear`，本条必须 `unclear`，**即使材料里有答案**；补丁最多 8 处，必须绑定 `span_id` 与逐字复制的 `original`，`replacement` 必须是可直接阅读的正文；无资料依据时返回空补丁，复查保留未解决项。这使「改稿」从一次性建议变成可复查、可留痕的协议。

### （六）创新应用四：有界执行、费用守卫与恢复一致性

- **幂等键**包含输入快照、轮次、阶段与适用的稿件版本；节点记录与业务产物同事务提交。
- **费用预留**在请求发出前持久化；请求已发出而响应未落盘时，用量标记为未知并**阻断后续请求**，不做自动重发，避免恢复流程重复收费。
- **租约与 fencing**：任务租约 30 秒、心跳 10 秒，旧 Worker 的迟到提交被拒绝，取消优先于结果写入。
- **有界停止**：单阶段尝试 3 次、返修 2 轮、补料 1 轮、单任务 24 次调用 / 160,000 Token、单次输出 3,000 Token、单阶段超时 180 秒。

### （七）创新应用五：描述性运营分析

运营分析是确定性规则执行器，不调用收费模型。对阅读/播放量 `v` 与某项互动次数 `x`，计算 `r = 1000·x/v`（仅当 `v` 非零且 `x` 已知）。基线只取同账号、同平台、同形式、同流量类型、同来源、更早且已观测的作品；观察窗口 24/72/168 小时，容许实际观察时长为目标的 100%—125%；某指标至少 3 条可用历史才展示中位数。输出为观察、可能解释与单变量实验建议，不作因果归因；指标修正使依赖它的分析与经验失效，经验撤销使引用它的计划转为需复查。

以上五项均为应用机制与工程实现层面的贡献。大模型、BM25、开源向量模型与 LangGraph 均为既有技术，本项目未训练基础模型，也不把角色数量当作创新效果证据——效果由第七节的对照实验回答。

### （二）辅助功能与数据隔离

网站用户拥有独立账号与资料空间，业务读写按 `owner` 与 `account_id` 双层隔离。登录会话可撤销；写操作校验 CSRF、来源与版本号；恢复码只存哈希，重设密码即撤销旧会话。资料更新保留旧版本，移出资料库仅排除新检索，不抹除旧任务证据。运营分析保存其依赖的指标标识，支持修正后的失效传播。

### （三）扩展性设计

- **模型扩展**：供应商适配器 + 统一契约测试，新增供应商只需实现适配层并通过同一组契约用例。
- **检索扩展**：重排器可替换为 cross-encoder 或学习式重排，替换前后用同一批固定样本与同一套指标做对照。
- **协议扩展**：平台授权、发布与指标回传按同一方式接入（OAuth 适配器 + 回调守卫），不改变创作主流程的状态机。
- **形态扩展**：本机版与内网版共用数据库迁移与配置契约，便于后续托管化。

### （二）关键实现片段

节点幂等键（`backend/runtime.py`）——与数据库事务、租约检查配合，避免已提交产物在重放时被重复应用：

```python
key = digest({'snapshot': state['snapshot'],
              'iteration': state['iteration'],
              'stage': stage,
              'draft': state['draft'] if stage in ('review', 'revise') else ''})
```

引用校验（`backend/live.py`）——三层任一失败即拒绝：

```python
require(source in lookup, '引用来源不在本次冻结快照')
require(quote in lookup[source], '模型引用无法匹配原始素材')
require(excerpt in draft_text, '审核引用无法匹配当前稿件')
```

### （四）部署方案

**Windows 运行包（推荐给评审复现）**：解压到本机磁盘 → 双击「一键启动.cmd」→ 启动器选择可用端口并打开浏览器 → 注册本地账号 → 导入资料 → 创作。首次运行在包目录内创建 `data`，保存本机账号、资料与任务；原始压缩包不含个人数据库、密钥或浏览器登录状态。

**源码部署**：安装 `requirements.txt` → 配置专用数据库与 `PUBLIC_ORIGIN` → 分别启动 `backend.api` 与 `backend.worker` → 打开 `http://127.0.0.1:8765/`。新增核心表通过 `backend/migrations.py` 顺序迁移并校验校验和；更新前备份数据库，已应用迁移不原地修改。

**运行时安全**：密钥仅在环境变量中，数据库使用最小权限账号；文档与日志不含真实密钥、Cookie、恢复码。

## 五、应用价值与展望

### （一）应用场景

**场景一｜数码家电选购图文**。创作者导入官方说明书与自购实测记录，系统按事实组检索规格，按样例组学习结构，按方法组确定开篇与节奏；型号校验拦住跨型号参数移植。成稿导出为 Word 确认稿，可直接在 Word/WPS 继续编辑。真实运行记录显示单篇成稿 10 次模型调用、74,520 tokens、成本上界 0.085 美元。

**场景二｜抖音口播与分镜脚本**。同一账号定位下切换目标形式，输出口播稿与分镜脚本，拍摄剪辑由创作者完成，工具不把脚本标记为成片。

**场景三｜持续运营复盘**。发布后回填链接与 24/72/168 小时指标，系统给出同口径观察、候选假设与单变量实验建议，经用户采纳后进入下一周计划。经验可撤销，指标修正会使依赖它的结论失效。

**场景四｜成稿前的读者验证**。用内容风洞把「这篇有没有讲清楚」变成 12 条可核查条件，逐条给出 `pass`/`unclear`，并对未讲清项生成绑定原句的局部补丁，复查保留未解决项。P20 Ultra 尺寸稿的实测中，原稿 12 条仅 4 条通过，风洞定位出 8 条未讲清项并给出实质补丁。

**场景五｜已有文案的二次优化**。把已发布的旧稿或待发文案直接导入内容风洞：先设定这篇必须答对的问题，再只用稿件本身判断讲没讲清，用材料核验有无依据，最后只对作者选定的问题生成绑定原句的补丁，并按原条件复查、保留未解决项。适合「稿子已经写了，但不确定读者能不能看懂」的情况。

**试用反馈（定性）**。目前已有数位个体小博主在自己的真实选题中使用，反馈集中在两点：流程更顺（从定选题到拿到可发稿件的步骤更清楚）、返工更少（复审与引用校验把问题提前暴露）。该反馈为口头与聊天反馈，尚未形成问卷与量化指标，故本文只作定性说明，不据此推断传播效果。

### （二）市场分析：需求基数、结构变化与竞争格局

**需求基数（可核实口径）**：截至 2024 年 12 月，我国网民规模 **11.08 亿**、互联网普及率 **78.6%**，生成式人工智能产品用户规模 **2.49 亿**（中国互联网络信息中心《第55次中国互联网络发展状况统计报告》，2025 年 1 月）。这说明两件事：内容生产的潜在用户基数极大，且使用生成式 AI 的习惯已经形成——缺的不是工具，而是可信的流程。

**结构变化**：其一，内容供给过剩，可信度成为差异化来源；其二，创作者资料（说明书、实测记录、课程笔记）大量沉淀，却很难进入写作流程；其三，平台对事实性表述的容错在下降。三点共同指向「可核对」，而不是「更快」。

**竞争格局**：通用对话工具（生成强、无资料治理）、通用内容编辑器（排版强、无 AI 协作）、运营记录工具（数据强、无创作）、AI 写作插件（功能点相似、缺版本与引用守卫）。有迹处在第三类与第四类之间：以创作流程为主体，以证据与审核为骨架。

**定位与商业化**：面向个人创作者与小团队的工具型产品，商业形态为工具授权或订阅。本方案**不引用未经核实的市场规模数字，也不对付费意愿做量化预测**——这两项应以真实用户数据验证，而不是写进参赛材料。

### （三）成果总结

1. 一套可运行、可打包、可恢复的多智能体创作与运营软件，含 Windows 免安装运行包与源码工程。
2. 四项可指认的机制性成果：三组解耦的分类证据检索、主张级引用闭环、内容风洞、有界执行与费用守卫。
3. 一套双层验证体系：1189 项后端测试 + 256 项前端测试的行为契约层，以及预注册题库 + 确定性指标 + 三组对照的质量指标层。
4. 真实模型条件下的对照数据：分类检索组事实支撑率 64.1%，相对单次直写 37.5% 提升 1.7 倍。

### （四）未来规划

个人开发者与小微品牌自建产品，在全球范围内都是增长最快的一类供给：做产品变得便宜，**把产品讲清楚、持续讲下去反而更贵**。有迹的定位就落在这里——不替用户做产品，而是把「把产品讲清楚」这件事变成可核对、可复用的内容流程：先把创作者自己的一篇稿子做扎实，再把这套流程借给需要宣传的产品方与中小公司。

| 阶段 | 目标 | 可验收指标 |
| --- | --- | --- |
| 近期 1—2 年 | 面向国内中小品牌与产品团队开放「产品推广型」使用：以企业账号接入，用有迹生产产品测评、使用教程与发布排期，帮助公司把产品讲清楚 | 签约中小品牌 10 家；每家累计成稿 ≥8 篇；一次通过率 ≥70%；单篇成本 ≤1 元 |
| 中期 3—5 年 | 对接海外主流社媒平台（图文与短视频，如 Instagram、TikTok、YouTube Shorts），把中国产品的卖点做本地化表达，减少语言、文化与合规带来的跨境推广门槛 | 接入 ≥2 个平台；覆盖 ≥3 个语种；海外账号内容产出周期 ≤3 天/篇 |
| 长期 5 年以上 | 形成「产品方—创作者—平台」三方撮合：产品方给事实与素材，创作者给表达，平台给分发，有迹做中间那层可核对的证据 | 撮合订单数、复购率、内容合规抽检通过率 |

跨境对接的前提是合规：数据出境、平台内容政策与当地广告法都要逐项评估，不做规避性设计；近期先把国内链路跑通，再谈海外。
