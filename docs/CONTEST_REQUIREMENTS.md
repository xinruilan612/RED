- 便于评审验证，可提供在线演示地址或安装包；需说明创新与差异化，可附真实用户反馈。
- 应具备易用性和兼容性，符合法规及行业要求，拥有自主知识产权或合法授权。

## 4. 本项目实现建议（非官方新增要求）

### 4.1 产品定位和范围

建议定位为“面向个人博主的多 Agent 图文创作工作台”。用户通过网页提供素材、选择选题、编辑和导出；后台承担模型调用与协作执行，用户无需本地配置开发环境。

v0.3 核心流程：Brief 与资料 → 受众洞察/素材研究并行 → 内容策划创作 → 主编审核 → 原创作 Agent 返修并复审 → 人工确认 → 模板导出。

按用户新图，4 个 Agent 分别负责受众洞察、素材研究、内容策划创作、主编审核；软件分 UI/Runtime Console、Orchestrator、Agents、Tools/Skills、Memory 五层。用结构化输入输出和明确的返修分支证明协作；每个 Agent 不必使用不同模型或独立服务器。技术选型与具体范围仍需在产品设计中确定，本文不锁定框架。

MVP 优先包含账号定位、草稿保存、局部修改、版本对比、模板封面、图文导出和任务恢复。热点抓取、自动发布、多账号运营、视频生成暂列后续候选，不自动加入当前范围。

“爆款”是用户期待，不是质量保证。没有真实发布和对照证据时，不宣称能预测爆款概率或提升某个百分比。

### 4.2 评分对应的项目证据

| 对应维度 | 建议积累的证据 |
| --- | --- |
| 创新性 | 与直接提示模型写文比较：素材依据、角色返修、人工控制带来的实际差异 |
| 技术实现 | Agent 输入输出、任务状态、持久化、重试和费用控制的代码及运行记录 |
| 功能完整性 | 从真实素材到可导出笔记的完整演示，包括补充资料、局部修改、失败恢复 |
| 方案完整性 | 架构图、流程图、数据设计、模型选型依据、测试记录、部署指南相互对应 |
| 应用价值 | 目标用户访谈和试用记录，记录完成时间、修改量、采用情况及样本条件 |
| 总结与展望 | 如实列明完成项、限制、失败案例和后续计划 |

这些是项目建议，不是评分保证。多角色名称本身不构成已验证的创新，模拟接口通过也不能证明真实模型质量。

### 5.1 建议的工程验收门槛

- 每次改动补充或更新相关测试，执行通过后创建对应 Git commit；不把未运行的检查写成通过。
- 测试真实流程、不同用户数据隔离、模型超时、重复提交、取消与重试、返修上限、刷新和服务重启后的恢复。
- 验证用户改稿后旧任务不会覆盖新版本；缺少素材时不会自动捏造亲历事实。
- 区分单元/集成测试、真实模型评测和用户试用。记录模型、提示词版本、任务样本、耗时和费用；费用上限另行确定。
- 对照实验使用一致素材和任务，比较普通单次模型生成与多 Agent 流程；如实报告失败样本，不能只挑成功案例。
- 检查源码、导出文件和日志不含真实密钥；保留第三方依赖与素材授权说明。

## 6. 推进顺序与提交前复核

1. 确认实际报名赛题、学校和赛区通知、队伍资格及截止时间。
2. 明确目标用户、核心流程、数据契约和每个 Agent 的职责，形成产品设计。
3. 开发可运行主流程，再完成编辑、保存、导出和恢复体验。
4. 进行工程测试、真实模型对照和小范围用户试用，修复问题并保存证据。
5. 根据实际成品编写说明、算法与测试报告，录制视频，验证演示环境。
6. 提交前逐项核验最新官方模板、格式、大小、时长、命名、截止时间及提交成功回执。
