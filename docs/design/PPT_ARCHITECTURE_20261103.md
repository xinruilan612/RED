需求边界沿用[正式需求](CONNECTED_CREATOR_REQUIREMENTS.md)。

依据2026年11月3日代码整理。技术栈已按实际依赖与调用代码核对；本次纠正原先将业务流程称为技术路线的表述。两张图分别用于“总体架构”和“技术路线”，不重复放在同一页。PNG可直接插入16:9幻灯片，SVG用于矢量缩放与后续修改。

## 一、总体设计

有迹面向需要宣传商品或服务的小红书创作者，把产品资料整理成可修改、可核对的文稿。系统沿用四个角色，在创作过程中加入需求覆盖、缺口提问和结构适配。最终稿由用户确认，系统提供复制和Word导出。

总体架构按职责划分为交互、接口与任务编排、创作处理、基础支撑。图中的层次表示模块分工，不表示每层单独部署一台服务器。

| 模块 | 设计与职责 |
| --- | --- |
| 创作工作台 | 接收主题、受众和产品资料，展示进度与证据，支持修改、复审和人工确认。 |
| 接口与任务编排 | FastAPI处理请求和权限；任务写入持久队列，由独立Worker执行；LangGraph组织阶段和暂停恢复。 |
| 分组检索 | 创作方法用于组织表达，样例用于参考结构，事实资料用于支撑本次内容。先过滤账号、领域等条件，再在组内排序。 |
| 四角色协作 | 受众分析与资料研究并行；内容角色依次完成策略、提纲、开头、标题和正文；主编角色审核当前版本。 |
| 创作决策 | 根据问题、证据和篇幅形成内容计划；识别值得询问的缺口；将样例段落功能适配到本次资料。 |
| 基础支撑 | 统一模型路由管理平台模型或用户配置；SQL保存业务状态、版本、证据与调用记录；检查点保存工作流进度。 |

数据库按部署配置选择PostgreSQL或SQLite，不要求两个业务库同时运行。SQL业务记录是权限、预算和批准的依据，工作流检查点不能替代这些记录。

## 二、技术路线：技术栈选型

| 技术部分 | 实际采用 | 具体用途 |
| --- | --- | --- |
| 前端 | HTML5、CSS3、原生JavaScript | 网页工作台、资料输入、改稿交互；Fetch API请求及轮询更新状态。 |
| 后端 | Python、FastAPI、Uvicorn、Pydantic | HTTP接口服务、请求参数校验和业务处理。 |
| Agent编排 | LangGraph、独立Python Worker、SQL持久队列 | 两个前置角色并行、内容阶段串行、人工暂停与检查点恢复。队列由项目SQL实现。 |
| 模型接入 | 平台DeepSeek、可配置Qwen等；OpenAI兼容HTTP协议 | 服务端统一模型路由、调用记录和费用控制。兼容协议不等于调用OpenAI模型。 |
| RAG检索 | 自实现BM25；可选Sentence-Transformers与本地BGE | 分组检索、余弦相似度与主题覆盖排序；向量不可用时明确降级BM25。 |
| 数据持久化 | PostgreSQL＋psycopg；SQLite＋sqlite3 | 按部署配置选用；保存任务、账号、证据、版本和费用记录。LangGraph使用对应检查点后端。 |
| 算法实现 | Python枚举、确定性贪心、启发式规则 | 实现需求覆盖优化、关键缺口提问排序和证据约束结构适配。 |
| 文档处理 | pypdf、XML、ZIP、OOXML | 读取文本型PDF和DOCX，生成Word稿件。产品导出不是python-docx实现。 |
| 安全 | PBKDF2、CSRF校验、cryptography/Fernet | 密码散列、请求保护和模型密钥加密。 |

本地BGE需要另行安装依赖并配置模型，不能将可选实现说成当前已加载验证。图中不把业务流程当成技术栈，也不将仅出现在依赖清单里的库一律标成已使用的核心技术。

## 三、实现流程

### 1. 整理资料，冻结本次依据

用户填写主题和产品资料，系统判断领域、渠道和内容形式，在当前账号的授权范围内检索。创作方法、表达样例、产品事实分别保存和使用，避免将样例中的经历或参数当成本次产品事实。

创作主路使用分组检索：向量可用时，结合余弦相似度与主题覆盖度排序；向量未配置或不可用时，按组降级为BM25。组内进行文档去重，并限制上下文长度。普通检索接口另有RRF融合实现，不能将它当作当前分组创作主路的执行方式。

联网是可选分支。已有资料库检索在创建任务时完成，授权的联网调查在角色执行前补充事实；不是所有网页都先进入资料库再检索。资料来源、版本和位置随任务保留，便于回查。

### 2. 并行分析，形成创作计划

受众角色提出读者关心的问题；研究角色整理有依据的事实、限制和缺口。两者完成后汇合，系统计算初步计划。内容角色提出选题策略和候选模块后，系统再更新计划。

三个算法属于同一个创作决策层，不是新增三个Agent：

| 算法 | 解决的问题 | 实现方式 |
| --- | --- | --- |
| 需求覆盖优化 | 篇幅有限，哪些内容应优先保留？ | 在预计长度预算内，最大化加权问题覆盖并惩罚重复覆盖。合法候选不超过12项时枚举子集，其余采用确定性贪心。 |
| 关键缺口提问排序 | 缺少多项资料，先问什么更有用？ | 按重要程度、新增受阻问题数、规则设定的可补充程度与成本排序。用户开启后最多一轮两问，可以跳过。 |
| 证据约束结构迁移 | 参考文章有体验或对比段，本次没有对应证据怎么办？ | 提取段落功能，匹配领域、渠道与形式，再按现有证据调整槽位。后续写作允许合并或省略槽位，不逐项堆成核对清单。 |

这些是针对创作场景的约束设计与工程实现，不主张首创最大覆盖理论、信息熵方法或篇章结构理论。规划覆盖是候选模块的预计覆盖，不能直接当作成稿事实准确率。

### 3. 按计划创作，保留用户要求

内容角色依次完成策略、提纲、开头、标题和正文。结构功能开启时，创作阶段使用抽取后的段落功能，不直接接收样例全文，避免继承原作者的经历与具体表达。

选中模块决定优先级，不是事实白名单；与主题相关且有依据的必要型号、适用条件、配件另售及保养要求不能因此遗漏。模块预计长度用于选材，不替代用户要求的正文长度。资料不足时缩小主张，不用无依据的内容凑字数。

### 4. 审核当前版本，由用户决定采用

主编对当前稿件提出问题，程序检查引用位置、部分事实风险、标题长度和版本关系。它们提供可回查的线索，不保证所有事实均正确。

用户修改后生成新版本，旧审核不能直接批准新稿；需要重新审核，或按系统提供的人工采用路径明确记录决定。最终稿可复制或导出Word，由用户自行发布。图中没有自动发布、爆款预测和涨粉保证。

## 四、PPT上可以直接使用的文字

### 架构图旁的说明

系统以FastAPI提供接口，由独立Worker执行持久任务，LangGraph组织四角色协作。资料按方法、样例、事实分组使用，三个决策模块负责内容取舍、缺口提问和结构适配。文稿经过审核后交给用户修改、确认与导出。

### 技术路线旁的说明

前端使用HTML、CSS和原生JavaScript；后端采用Python与FastAPI，Uvicorn提供服务，Pydantic校验输入。四角色由LangGraph和独立Worker组织，任务与检查点持久保存。检索采用自实现BM25，支持可选本地BGE；数据按配置保存到PostgreSQL或SQLite，模型通过统一HTTP接口调用。

### 约一分钟讲稿

有迹主要解决的是小红书创作者拿到产品资料后，怎样组织出一篇能用的文稿。

首先，资料分成创作方法、表达样例和产品事实，分别使用。受众分析与资料研究同时进行，一个关注读者想知道什么，另一个确认手上有哪些依据。

随后，三个决策模块参与创作：篇幅不够时选择重点，信息缺失时判断先问什么，参考文章的结构也要按本次证据调整，不能把别人的体验直接搬过来。内容角色再完成策略、提纲、标题和正文。

最后，主编提出审核意见，程序核对引用和版本。用户仍然可以修改并复审，确认后复制或导出。我们的改进重点是让内容取舍有依据、修改过程可回查；并不把模型审核当成事实保证，也不承诺生成之后一定成为爆款。
