## 2. 现有代码与目标差距

此前 app/orchestrator.py 使用 asyncio.gather 做受众/素材并行，之后策略、写作、审核、独立改稿；app/schemas.py 的状态仅 running/completed/failed。循环结束无论是否审核达标都标 completed，不能直接映射新设计 SUCCEEDED。

现有 ui.py 展示 traces 和“发布前请人工确认”文字，尚无持久化确认 API。SQLite 存运行结果不等于 Profile/Material/History 检索系统；已有模型输出和 JSON 校验不等于实现工具调用。Streamlit / FastAPI / SQLite 原型可继续用于流程验证。

此前解压后的大部分 starter 源码未纳入 Git；收尾时已发现旧目录移除。本轮不恢复、提交这些删除或批量加入用户的其他文件。正式迁移前应排除 .env、数据库、缓存和虚拟环境，建立可复现源码基线，再变更运行逻辑。

## 4. 数据与兼容

旧 WorkflowState 保留 schema_version=1 只读映射：strategy → content_artifacts.strategy，draft → legacy_candidate；traces 保留 legacy 标记。旧 completed 不推断人工接受或发布；缺少 evidence/confirmation 时需新审核。

新增 API 使用 /api/v1；WorkflowState/RuntimeEvent 使用 schema_version=2，角色产物使用 1.1.0，原 /api/runs 在迁移期保持旧契约或明确废弃日期，不静默改变字段含义。数据库先备份并做迁移演练，配置和模型密钥不写进迁移脚本。

## 运营闭环 v0.4 推进计划

方案依据：[v0.4 技术提案](ARCHITECTURE.md#运营闭环-v04-技术提案)。

本轮是需求、文档与技术设计，不实施下表。保留已有 backend/、frontend/、docs/、tests/、runtime/，不新建项目副本或文件夹。当前源码基线 a561323，旧 starter 的三处未提交删除不纳入本轮。

| 阶段 | 实施范围 | 验收门槛与依赖 |
| --- | --- | --- |
| O0 本轮 | 存档、现有 Demo 复跑、六环节设计和国内接口调研 | 文档检查、原有产品测试通过；新能力明确标未实现 |
| O1 选题到创作 | 一个有来源的热点输入、时间/去重/账号匹配、选题进入原四角色 | 过期/失败不冒充实时；冻结快照；原有生成/返修/确认回归通过 |
| O2 人工运营闭环 | 平台内容规格、候选版本、人工发布记录、指标导入、复盘及经验确认 | 绑定真实帖子；缺失/窗口/去重验证；经验接受/回滚；不宣称 API 自动发布 |
| O3 一个国内官方通道 | 选权限可获批的平台，OAuth、发布批准、回执和指标适配 | 实际获权、测试账号真实发布及指标返回；处理中/失败/未知/重复提交实测 |
| O4 可控实验与生产化 | 样本积累、经验检索效果评估、账号系统、持久后台任务 | 对照证据、隔离、恢复和费用门槛通过，再考虑第二平台 |

实施前确认：小红书/抖音哪个账号先试、账号及开发者资质、可用热点源、抖音图文或用户成片、可用于复盘的历史数据、费用额度。没有官方权限时 O1/O2 仍可推进，但 O3 不得标完成。LangGraph 迁移按适配层逐步替换，不与新增所有能力捆绑成一次大重写。

创作 v0.3、运营提案 v0.4、角色 schema 1.1.0 是不同版本域；本轮不提升运行 schema。未来增加 Publication/Metric/Learning 数据后，先演练数据库备份和迁移，再更新机器契约、独立卡片与合并文档，并通过对应测试、独立 commit。
