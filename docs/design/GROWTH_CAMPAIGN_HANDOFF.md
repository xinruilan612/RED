# 有迹内容试飞台：团队接手说明

> **当前需求（2026-10-10，已授权实施）**：[小红书连接、研究资料库与多模型](CONNECTED_CREATOR_REQUIREMENTS.md)。新增能力以该基线为准；下文旧阶段限制和完成记录保留其日期与实现边界，不作为拒绝新需求的依据。

这份说明给继续开发有迹的队友看，回答四件事：项目要解决什么问题、现有代码做到了哪一步、下一步按什么顺序推进、怎样证明完成。它是产品执行说明，不代替参赛官方要求；规则入口见 [参赛要求与交付对照](../CONTEST_REQUIREMENTS.md)。

## 产品方向

**有迹是个人创作者的内容试飞台：评论区需求 + 搜索意图 → 可证伪假设卡 → 风洞预演 → 小流量赛马 → 实盘归因 → 同账号私有经验账本。**

它面向想卖货的商家、想涨粉的创作者、想为工具或活动获客的运营者。用户不是来“再生成一篇文案”，而是把一个具体推广目标变成可检验的内容方案，逐步用读者反馈、试验结果和发布后数据判断它是否对这个账号、平台和目标有效。

一句话给队友解释：**先弄清受众在找什么，再写清我们认为哪种内容会促成什么行动；发布前排查主张和证据，发布后比较真实结果，最后只把有证据且用户确认的结论记成可撤销经验。**

## 解决什么问题

现在创作者经常凭感觉选题、让通用 AI 写稿、看播放量判断成败。播放高不等于涨粉、成交或有效线索；教程里说“热度高就能做”“用了某工具就能避免限流”，也不等于有证据。复盘时容易事后挑指标、忽略分母和投流差异，错误经验还会被下一轮继续使用。

有迹把推广目标、受众信号、内容版本、指标口径、观察窗口和结果连起来，让用户在发布前先规定“什么结果支持我、什么结果推翻我”，发布后知道数据能说明什么、不能说明什么。

## 为什么不是豆包加一张风控清单

通用模型可以写文案，也能按提示检查。项目价值不能建立在“用了多个 Agent”或“检查项更多”上，而应建立在跨阶段可追溯的数据关系和证据纪律上：

- 评论区需求和搜索意图分别保存来源、时间、样本和取得方式，不揉成来历不明的热点分数。
- 假设在看结果前固定主要目标、指标、分母、门槛、观察窗口和反证条件，不能发布后再挑一个好看的数字。
- 风洞只做发布前筛查；赛马记录版本和样本比较；实盘归因绑定真实内容、链接和业务结果。模拟、人工回填、观察性比较都明确标注，不能伪装成平台核实或因果证明。
- 经验限定到账号、平台、目标和适用条件；证据不足时保持待验证，数据修正或新证据反驳时可以失效和撤销。

这是项目要验证的差异，不宣称全球首创或保证爆款。必须与“豆包直出 + 普通人工审稿”做同材料盲测，比较重大无依据主张漏检、误报、目标与 CTA 匹配、修改耗时及作者采纳情况。

## 三种推广目标，共用一套试验流程

| 目标 | 主要结果例子 | 不能拿来替代主要结果的指标 |
| --- | --- | --- |
| 帮商家卖货 | 商品有效点击、加购、订单、成交额或退款 | 曝光、播放、点赞 |
| 帮创作者涨粉 | 每千次有效曝光新增关注、主页访问转关注、后续留存 | 单篇播放或点赞 |
| 帮工具/活动获客 | 有效试用、报名、咨询、激活、合格线索 | 普通链接点击 |

每张假设卡只定一个主要目标和主要指标，其他数字只用于解释过程。

## 内容风控在什么位置

风控是整条推广验证链里的可信度护栏，不是独立敏感词扫描，也不是内容可读性总分。它至少检查：产品功能、价格、兼容和活动期限有没有当前材料支持；“保证涨粉/爆款/提升三倍”等结果承诺有没有基线和可核对数据；赞助、佣金、赠品、素材版权和个人信息是否有披露/授权；内容是否兑现选定受众和主要行动；实验数据是否真实、分母和窗口是否完整、是否混入模拟或付费流量。

检查结果要指出原文位置、来源、适用条件和缺失证据，并区分已支持、没讲清、材料不支持、证据不足。不能承诺“不会限流”或“保证合规”，不能只根据教学视频自动造规则。

## 现有项目状态

以当前分支的源码和测试为准，不要只看早期设计文档。现有代码已经有正式网站、账号隔离、创作工作流、内容风洞、后台 Worker/持久任务等底座。**“假设与试飞”第一段也已实现：**可记录评论需求/搜索意图，建立卖货/涨粉/获客假设，绑定稿件和风洞任务，登记 A/B 版本和人工发布/指标，进行三阶段人工裁决，并在同账号范围引用探索性经验。

现有实现仍有边界：风洞模拟不是真实模型效果；A/B 是用户登记的原始比例，没有随机分流和统计检验；发布链接与指标由用户人工回填，没有平台核验、自动发布、自动抓数、UTM/订单回传；没有真实推广效果证据。细节见 [产品方案](GROWTH_CAMPAIGN_PRODUCT.md)、[实现进度](../IMPLEMENTATION_STATUS.md)、[风洞工程报告](../windtunnel/ENGINEERING_REPORT.md) 和 [集中待办](../windtunnel/OPEN_ITEMS.md)。

## 继续开发顺序

### P0：把“假设 → 试飞 → 结果”做成可用的网页闭环

先补浏览器端到端流程：创建信号、建假设、生成/选择内容版本、风洞绑定、录入 A/B 结果、录入发布观测、完成人工裁决、查看经验引用；失败、刷新、重复提交、过期版本和跨账号访问也要覆盖。让第一次使用的创作者能在界面上理解下一步，而不是依赖 API 或开发者口头解释。

**验收：**在干净测试账号从头到尾走通；稿件、账号、假设、风洞报告和指标的关联在刷新及服务重启后仍正确；错账号、错版本、模拟数据冒充真实结果都被阻止；用户可看到每个结论的来源和证据限制。

### P1：验证检查和假设卡是否真的帮到人

按 [研究方案](../windtunnel/STUDY_PROTOCOL.md) 收集有授权的样本。探索样本用于修订规则，留出样本冻结规则后再评估。与“豆包直出 + 普通人工审稿”比较同一素材和目标下的漏检、误报、修改成本、可读性/目标匹配和作者采纳情况；真人试读记录原始答案和缺失，不把团队自建样例写成外部用户反馈。

**验收：**有明确样本数、授权来源、版本冻结、盲评方法、原始记录和失败样本；结果不足或不优于基线时，改流程或缩小方向，不用增加 Agent 数量掩盖问题。

### P2：提高小样本比较的可靠性

继续明确样本单位和分配规则，能随机时记录随机方式；不能随机时明确标记观察性比较。展示分母、数据来源、异常样本、观察窗口、缺失和不确定性；按实际数据量选择描述统计或区间估计，不将原始百分比叫“显著提升”。涉及平台赛马先核实平台规则和账号许可。

**验收：**同一组数据可复算；界面区分随机试验与观察记录；样本不足时主动显示“证据不足”；没有把用户登记的结果写成平台验证。

### P3：实盘归因与经验账本

先支持安全、可解释的人工导入与关联，再评估有官方权限的平台接口。把内容哈希、账号、发布时间、追踪链接、主要转化、自然/付费来源和观察窗口连起来。经验经用户审核才生效，带样本、证据等级、适用范围、有效期和反例；指标更正、账号变更或证据被推翻时使依赖计划失效。

**验收：**缺失指标不补零；无可靠归因时标记未知/关联；模拟和真实数据分开；经验可追踪、复核、撤销；未获授权的 API 能力清楚显示未接入。

### P4：再决定真实模型、平台接入和部署范围

先凭离线盲测确定模型调用有无增益，再由项目负责人单独定模型、预算和授权；模型调用须留供应商/模型/提示版本、输入来源、用量与费用。平台发布/取数以官方权限、账号授权和实测回执为准。公网部署另做访问控制、备份恢复、日志和稳定性验收，不把本地演示写成生产服务。

## 工程约束与协作方式

- 从现有 backend、frontend、PostgreSQL、Worker 和运营模块扩展；先读 [架构与模块入口](README.md) 和 [迁移计划](MIGRATION.md)。不另建平行后台、不重写现有创作主流程，不把业务状态只存在浏览器。
- owner/account 隔离、服务端权限、版本校验、幂等、事务、预算保护、取消/恢复和审计必须延续。数据库只追加迁移，运行时新数据必须保留来源快照。
- 真实与模拟、人工回填与平台核验、随机实验与观察性比较分别建模、分别呈现。
- 用户授权、平台规则、数据来源和版权要能追溯。不要自动抓取私人评论、自动发布或联系受试者。
- 每项改动先明确用户行为和验收条件，再实现并更新相关测试；测试真正运行通过后提交对应 Git commit。不要把工作区已有的三处删除加入提交：`xhs_multi_agent_starter/app/backend_http.py`、`xhs_multi_agent_starter/tests/test_backend_http.py`、`xhs_multi_agent_starter/ui.py`。
- 至少按仓库要求运行真实 PostgreSQL 集成测试、全量 unittest、所有前端脚本 `node --check`、角色卡一致性检查和 `git diff --check`；跳过不算通过。涉及 UI 时要做实际浏览器验收，涉及部署时要在独立环境按部署说明复现。
- 每个阶段交付代码、测试结果、真实/模拟边界和未完成项，不要只交计划或截图。
